# 0003 — Windows 11 style custom title bar

- **Date:** 2026-10-08
- **Session:** 0003
- **Status:** 🟡 partial (title bar works; the top edge of the caption is a known
  limitation, see *Pending / TODO*)

## Objective

Replace the native Windows caption with a title bar drawn in Flutter, in the
Windows 11 style, without clashing with the app theme and without breaking the
native window behaviors (move, resize, minimize, maximize, close).

## Decisions made

- **Fully custom title bar** (not just recoloring the native caption): hide the
  native caption with `TitleBarStyle.hidden` and draw the bar with Flutter widgets.
- **Stack:** `window_manager` 0.5.2 (window control + real Windows 11 caption
  buttons) and `flutter_acrylic` 1.1.4 (Mica backdrop).
- The bar lives in `MaterialApp.builder`, **above the `Navigator`**, so it stays
  put across every route.
- Reuse `window_manager`'s **real** Windows 11 glyphs (`WindowCaptionButton`,
  correct hover/pressed states) instead of drawing our own icons.
- Keep **all** native window calls isolated in `WindowController`; nothing else
  talks to `window_manager` or `flutter_acrylic`.
- The bar background is **opaque** (not transparent). See *Problems encountered*.
- `MainAxisSize` / layout: the bar is 32 logical px tall, matching the Win11
  caption.

## What we did

1. Added the two dependencies and let `pub add` regenerate the plugin registrant.
2. Created `WindowController` (app-shell concern): `Window.initialize()`,
   `windowManager.ensureInitialized()`, `WindowOptions` (hidden caption, centered,
   minimum size), Mica effect, and helpers (`minimize`, `maximize`, `unmaximize`,
   `close`).
3. Created `TitleBar`: app icon + name on the left, the three real Win11 caption
   buttons on the right, wrapped in `Material` and an opaque background.
4. Wired it through `MaterialApp.builder` as `Column([TitleBar, Expanded(child)])`,
   so it renders above the `Navigator`.
5. Removed the placeholder `AppBar` from `HomeScreen` to avoid a duplicate title.
6. Wrote a small `_TitleBarDragArea` to work around `window_manager`'s
   `DragToMoveArea` not being able to move a maximized window.
7. Verified with `flutter analyze`, `flutter test`, a Windows build, and real runs
   (screenshots + synthetic mouse input via `SendInput`).

## Relevant code

Bootstrap (`lib/main.dart`):

```dart
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  await WindowController.initialize();
  runApp(const AgustreamApp());
}
```

Mounting the bar above the `Navigator` (`lib/app/app.dart`):

```dart
builder: (context, child) {
  return Column(
    children: [
      const TitleBar(),
      Expanded(child: child ?? const SizedBox.shrink()),
    ],
  );
},
```

Moving a maximized window (`lib/ui/widgets/title_bar.dart`): `window_manager`'s
own `DragToMoveArea` calls `startDragging()`, which sends `SC_MOVE`. Windows
refuses to start a move loop on a maximized window, so the drag silently does
nothing. The workaround restores the window first:

```dart
Future<void> _startDragging() async {
  if (isMaximized) {
    await windowManager.unmaximize();
  }
  await windowManager.startDragging();
}
```

## Problems encountered

1. **Crash on launch — missing binding.** `Window.initialize()` (flutter_acrylic)
   threw *"Binding has not yet been initialized"*. Fixed by calling
   `WidgetsFlutterBinding.ensureInitialized()` before touching any plugin. Neither
   `flutter analyze` nor `flutter test` catch this; only a real run does.

2. **Caption glyphs "glitched" when maximized.** The bar was transparent so the
   Mica backdrop could show through. A transparent region is **not repainted** when
   the window is resized, so the previous glyphs stayed behind as a double image
   (verified with a 14× zoom: the minimize line was drawn twice, offset). Fixed by
   giving the bar an **opaque** `Material` background.

3. **Yellow underline under the app name.** The `Text` was outside any `Material`,
   so it merged with `DefaultTextStyle.fallback()` (white text with a yellow
   double underline). Fixed by wrapping the bar in `Material`, which also provides
   the theme's text style.

4. **Cannot drag a maximized window.** Reproduced with synthetic input: while
   maximized, a drag produced `delta=(0,0)`. Fixed with `_TitleBarDragArea`
   (restore before dragging).

5. **Top edge dead zone — OPEN.** See *Pending / TODO*.

## Measurements (for reference)

Display is 2560×1440 at 125% DPI (`dpr = 1.25`), so 8 physical px of frame ≈
10 logical px.

| Window state | Window rect (physical) | Flutter view | Dead zone (top of bar) |
| --- | --- | --- | --- |
| Windowed | `(480,240)-(2080,1140)` | `(488,241)-(2072,1132)` | first ~4–11 px |
| Maximized | `(-9,-9)-(2569,1389)` | `(0,0)-(2560,1380)` | first ~12–19 px |

The bar is 40 physical px tall, so the dead zone is a meaningful part of it.

## Pending / TODO

### 1. Top edge dead zone (resolve to 100%)

**Symptom.** The top ~10 px (windowed) / ~15 px (maximized) of the custom title
bar receives no pointer events: it is neither draggable nor resizable. Everything
below that works.

**Cause.** It is a Windows non-client area issue, not a Flutter one. Windows
reserves the outer frame (`WS_THICKFRAME`, `SM_CXSIZEFRAME + SM_CXPADDEDBORDER`)
for resizing and hit-tests it as non-client (`HTTOP`). `window_manager`'s
`TitleBarStyle.hidden` keeps that frame (to preserve native resizing) and only
insets the client on the left/right/bottom, so the top border overlaps the client
and swallows those clicks. This is **not documented** by the library; its
`CHANGELOG` shows the area has been patched many times.

**Attempted and discarded.** Handling `WM_NCHITTEST` in
`windows/runner/win32_window.cpp` had **no effect**: the top-level window never
receives the message, because the Flutter view is a **child window** that owns the
pointer. The experiment was reverted.

**Options to finish it:**

- **Option B — `WM_NCHITTEST` on the Flutter child window (best result).**
  Subclass the child (`SetWindowSubclass`) in the runner and return `HTCAPTION` for
  the title-bar strip and `HTMAXBUTTON` for the maximize button. This gives
  **native dragging** (removing the need for `_TitleBarDragArea` and its
  `SC_MOVE` timing) and **restores the Windows 11 Snap Layouts flyout**. Cost: the
  native proc does not know where the Flutter buttons are, so the geometry has to
  be agreed/duplicated (e.g. "first N px minus the right ~140 px") and converted
  with `GetDpiForWindow`.

- **Option C — truly frameless window + resize from Dart (most self-contained).**
  Remove `WS_THICKFRAME`/`WS_CAPTION` in the runner and handle `WM_NCCALCSIZE`
  (do **not** rely on `windowManager.setAsFrameless()`: in 0.5.2 it only sets a
  flag). With no frame there is no border to steal clicks, so the dead zone
  disappears. Resizing is then done in Dart with `DragToResizeArea`. Cost: resize
  is slightly less native; DWM shadow/rounded corners need re-checking.

- **Option A — accept it (current choice).** Drag from the middle of the bar.
  Zero cost; the limitation is cosmetic.

### 2. Mica is currently invisible

Because the bar is opaque and the `Scaffold` is opaque, nothing shows the Mica
backdrop anymore, so `flutter_acrylic` is effectively inert. Decide later: either
remove the dependency, or reintroduce a translucent surface (which brings back the
ghosting problem unless the repaint issue is solved).
